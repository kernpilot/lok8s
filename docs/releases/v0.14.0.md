---
title: lok8s v0.14.0
---

This release adds one feature: a service profile can carry kustomize patches.
It also has a dependency update for two Go vulnerabilities. It ships the
changes merged since
[v0.13.0](https://github.com/kernpilot/lok8s/releases/tag/v0.13.0).

## Security

- `golang.org/x/net` v0.62.0, for GO-2026-6866 and GO-2026-6860 (#338).

## Changes

- **Service profiles can patch manifests** (#339). `services.<name>.patches`
  (in `services.yaml` or a `services.<config>.yaml` profile) is a list of
  `{target, patch}` entries. `lo env kustomization` adds them to the
  generated Tilt overlay, so a profile can change more than the image. For
  example, a profile that runs a dev server can give it a writable root
  filesystem and a larger memory limit, while the default build keeps the
  hardened settings. `lo build` and the committed manifests do not change.
  - A patch applies only to objects of its own service: lo adds the label
    selector `lok8s.dev/name=<service>` to the target.
  - `kind` and `name` are required in the target; `group`, `version` and
    `namespace` are optional. Each value is matched exactly. An object
    without a namespace counts as `default`, as in kustomize.
  - kustomize ignores a patch whose target matches nothing. lo does not:
    `lo env kustomization` checks each target against the domain artifact
    and fails the run, naming the patch, before it writes the overlay.
  - One exception: do not set `namespace` in the target of a cluster-scoped
    object (a ClusterRole, a Namespace). The check cannot tell which kinds
    are cluster-scoped, so such a patch passes the check, and kustomize then
    applies it to nothing.
  - The patch text goes through `envsubst` like every merged value, so the
    strategic-merge `$` directives cannot be used: write a JSON patch to
    delete or reorder.
  - Both implementations (the binary and the frozen bash tree) produce the
    same overlay. `lo lint` and the Tilt extension accept the new key.
  - See [Patching a service's manifests from a profile](https://lok8s.io/guide/services#patching-a-service-s-manifests-from-a-profile).

## Upgrade

- **First, update the pins.** Pin `lo`, the `kustomize-secret` plugin and
  the `.lok8s` env ref to `v0.14.1` (the v0.14.0 code with the version
  fixed, see the known issue), and run `b update`. Do this before the
  steps below: `lo assets diff` and `lo assets update` compare against the
  files inside the `lo` you run.
- Nothing else to do for a project without `patches`: its overlay is
  byte-identical to v0.13.0.
- A project that ejected the Tilt extension (`.lok8s/tilt/`) runs
  `lo assets update tilt` before it uses the new key: the old extension
  refuses unknown service keys. If you changed your copy, `lo assets update`
  refuses it: run `lo assets diff tilt` and merge by hand.
- A project with its own bash tree in `.lok8s/` (`lo assets eject bash`)
  runs `lo assets update bash` to get the bash twin of the change. Until
  then, a command that runs on the bash implementation drops the patches
  without a word, and its `lo lint` refuses the key.

## Known issue

The v0.14.0 tag was cut before the version references were updated. Its
release binaries report 0.14.0, but these report 0.13.0, because they take
the version from the `VERSION` file:

- the bash tree inside the binary and in the framework tarball. So do a
  tree from `lo assets eject bash` (only its `.lo-origin` says 0.14.0), a
  `.lok8s/` synced from the v0.14.0 env ref, and a `lo version` or inventory
  that runs on the bash implementation;
- the operator image `ghcr.io/kernpilot/lok8s-operator:0.14.0`;
- a `lo` built from the v0.14.0 source (`make build` or a plain `go build`).

The code is the v0.14.0 code. [v0.14.1](https://github.com/kernpilot/lok8s/releases/tag/v0.14.1)
fixes the version, and its release workflow now stops a tag that does not
equal the `VERSION` files. Use v0.14.1.
