---
title: lok8s v0.14.1
---

This release fixes the version that the bash tree and the operator image of
[v0.14.0](https://github.com/kernpilot/lok8s/releases/tag/v0.14.0) report.
The code is the v0.14.0 code; read its notes for the changes.

## Fixes

- **Every artifact reports its own version.** v0.14.0 was tagged before its
  version references were updated. Its release binaries report 0.14.0: they
  take the version from the tag (`lo version`, the inventory, the
  `lo toolchain install` header). These report 0.13.0, because they take it
  from the `VERSION` file:
  - the bash tree inside the binary and in the framework tarball
    (`.lok8s/VERSION`). So does a tree from `lo assets eject bash`, and a
    `lo version` or a ClusterInventory that runs on the bash implementation;
  - the operator image `ghcr.io/kernpilot/lok8s-operator:0.14.0` (and
    `:0.14` and `:latest`, until this release moves them): its `lo` is built
    with the version from `VERSION`.

  In v0.14.1 both `VERSION` files read 0.14.1.
- **A tag must equal the VERSION files.** On a tag, the release workflow and
  the image workflow now stop before they build anything when the tag does
  not equal both `VERSION` files (`hack/check-release-version.sh`).

## Upgrade

- Pin `lo`, the `kustomize-secret` plugin and the `.lok8s` env ref to
  `v0.14.1`, and run `b update`.
- If you run the operator image, use `ghcr.io/kernpilot/lok8s-operator:0.14.1`.
- A project with its own bash tree in `.lok8s/` (`lo assets eject bash`)
  runs `lo assets update bash`, which writes the new `.lok8s/VERSION`. Until
  then, `lo assets diff bash` lists `VERSION` as `lo updated`.
- The bash tree only prints `VERSION` (`lo version`, the inventory,
  `lo status`). The binary's own version also sets the plugin version that
  `lo toolchain install` writes and `lo doctor` expects: in the v0.14.0
  release binaries it is 0.14.0, so that is right. Only the `lo` in the
  v0.14.0 operator image has 0.13.0 there, and the image does not run those
  commands.
